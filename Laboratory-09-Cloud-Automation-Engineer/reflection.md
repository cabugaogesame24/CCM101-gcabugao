# Reflection

Automation is essential when managing hundreds of cloud servers because manual work becomes impossibly slow, inconsistent, and prone to slip-ups. Scripts and scheduled tasks run exactly the same way every time and finish instantly across all machines — keeping configurations uniform, freeing staff for important work, and scaling without needing extra hands for each additional server.

Yet automation carries real risks: a typo such as deleting the wrong folder can repeat automatically everywhere, destroying data or disrupting services across the whole fleet before anyone notices. Errors compound quickly when the same script runs on 1,000 machines — a small mistake becomes widespread damage, so testing, reviewing code, and adding safety checks before deployment are absolutely necessary.

Writing a Bash script felt different from creating a Docker Compose YAML file because Bash uses procedural logic — commands run step by step and can make decisions or calculate values — whereas YAML describes the desired setup in a more declarative style, listing services and settings without the flow of instructions. Both serve automation, but Bash feels like writing a set of actions while YAML defines what the final state should look like.

Looking back from Laboratory 1 up to now, my view of cloud computing has grown from just knowing basic terms to understanding a complete workflow: designing infrastructure, deploying applications, handling data, running operations, hardening security, and finally automating everything. I no longer see the cloud as a vague concept — I can build, protect, and manage real working systems end to end.

I most enjoyed the Security Engineer role because securing systems felt like defending something real — closing doors, checking every connection, and protecting data from threats. It required careful attention and rewarded thinking ahead, which felt both practical and very meaningful.
